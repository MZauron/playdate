# QUESTIONS — decisions still open

Each question has an id, the default we build with until it is answered, and what it affects.
When one is answered: write the answer under it with the date and who decided, update DESIGN.md (and the rule or setting), and tick it.
Q1, Q4, Q5, Q7, Q8, Q9 and Q14 come from the design doc's own "Open questions"; the others came up while turning the doc into a build plan.

## Needed before Phase 1
- [x] **Q3 Every text needs the organizer to tap Send, once per friend.** **Answered (owner, 2026-11-16): the default, as built.** Texts come from the organizer's own number (doc), so Kindred can only open Messages with the text filled in (an `sms:` link); it cannot send by itself. Each friend has their own link, so it is one tap per friend. That also applies to the confirmation and update texts. Is that OK? Default: yes; after Send invite, Confirm and send update, and Send update, a list shows **Text Aisha**, **Text Dev**…, each ticking when tapped.
- [ ] **Q10 Who sends the sign-in code, and to which countries?** Supabase phone sign-in needs an SMS provider (Twilio Verify, MessageBird or Vonage), paid per code. Default: Twilio Verify through Supabase, Canadian and US numbers (+1) only at launch.
- [x] **Q12 Friends' phone numbers on the server.** **Superseded by Q26 (2026-11-16): friends' numbers are no longer stored; only the keyed hash is.** The doc says numbers are stored "in a protected form". Kindred needs a friend's number for every later text (confirmation, update), from any phone the parent signs in on. Default: kept in the owner's private `friends` rows (RLS, never shown to anyone else, never logged), plus a keyed hash for matching; encryption at rest added before the beta (Phase 3).
- [x] **Q15 Adding friends without a contact picker.** **Superseded by Q26 (2026-11-16): the parent picks the person in their own share sheet; typing a number only checks who uses Kindred.** Kindred is a web app (owner's decision, 2026-11-14). iPhone browsers cannot open the contacts list, so on iPhone a parent types a friend's name, child's name and number (or pastes the number); Android Chrome gets "Choose from contacts". Is typing acceptable for the first version? Default: yes; friends added once are reused, and groups make repeat playdates one tap. If test parents find it too slow, wrap the web app in a native shell later (Capacitor or Expo) just for the contact picker.
- [ ] **Q16 Name and domain.** The doc's links use `kindred.app`. Is it bought, and has the name been checked for clashes? Default: build with the Railway domain; the link domain is one setting (`PUBLIC_LINK_BASE`).

- [x] **Q17 What a friend is called in your list.** **Answered (owner, 2026-11-16): the default, as built.** The doc shows "Arjun's dad", but nobody tells Kindred whether the parent is a dad, a mom or someone else, and guessing from a name would be wrong. Default (T07): the label is "Arjun's parent" (from the child's first name), the parent can rename it, and the child's first name is required when adding a friend (the playdate title, KD-06, is built from it). Is that right, or should Add a friend also ask "Mom / Dad / Other"?

- [x] **Q18 What "Your name" on the Plan screen changes.** **Answered (owner, 2026-11-16): the default, as built.** The doc lists "Your name" under Details, and the invite page shows "Alex · Mia's parent", but a playdate has no name of its own. Default (T08): the box starts with the parent's first name from Setup; changing it changes `profiles.first_name`, so every invite (old and new) shows the new name. Should it instead be a name for this one playdate only (a new column)?

- [x] **Q19 What the update text says, and whether it has a link.** **Answered (owner, 2026-11-16): the default, as built.** The doc says "Text with the update + link". Only the sha256 of each link is stored, so sending a link again means making a new one, and the friend's first link would stop working (even for friends the organizer never texts). Default (T16): links never change; after Send update, families who stay get a short text with the new day, time and place ("New time for our playdate: … Please answer again with the link above." / "Our playdate has an update: … The link above has the details."), and families just added get the full invite with their own new link. Is that right, or should every update text carry a fresh link (and the old one stop working)?

- [x] **Q20 Texting an invite again from another phone, or after a day.** **Answered (owner, 2026-11-16): the default, as built.** Links are stored only as hashes, so the Text buttons exist only on the phone that sent the invite: that phone keeps them for a day (C2), and the playdate page shows the ones not sent yet. Default: nothing more. Alternative: a "Text a new link" button per friend on the playdate page, which makes a new link for that friend and retires the old one (the first text's link would then say "This link doesn't work"). Wanted?
- [x] **Q21 The quick chips under Find a place.** **Answered (owner, 2026-11-16): the default, as built.** The doc shows "search + chips" without naming the chips. Default: Parks, Playgrounds, Indoor play, Libraries, Splash pads (one list in `en-CA.ts` as `places.quickSearches`; each one simply searches those words). Other chips wanted?
- [x] **Q22 When a place counts as liked or popular.** **Answered (owner, 2026-11-16): the default, as built.** "Parents who like it" and Popular with parents show counts only. Default: a count shows only once at least two parents hearted the place (`MIN_PARENTS_SHOWN` in `src/lib/domain/favourites.ts`), so one parent's choice is never visible on its own; Popular lists the top 10. A different minimum?
- [x] **Q23 What happens to invites when an invited parent deletes their account.** **Answered (owner, 2026-11-15): the default, built in T24.** The doc doesn't say. Default (owner's choice, 2026-11-15): their invites are removed from other parents' playdates, with their answers, so the organizer's page no longer lists them; the organizer's contact for them stays as a text friend. Migration 0010 (T24).

## Needed before Phase 2
- [x] **Q2 Who sends the "most families picked" text (KD-12)?** **Answered (owner, 2026-11-16): the default, as built.** It is triggered by other parents' answers, not by the organizer, so it cannot come from the organizer's phone by itself. Default: it shows on the organizer's Home under Needs you ("Text Aisha: most families picked Mon 9–12") with a Text button; still once per invite.
- [x] **Q4 Families with more than one child** **Answered (owner, 2026-11-16): the default, as built. Reopened by Q30 (2026-11-18).** (doc). Choose which child a playdate is for, and let friends tick which of their kids are coming? Default: not in v1; the title uses each family's first child; Setup still stores all children.
- [ ] **Q6 Where place search comes from.** The earlier kit used Google Places. Its terms allow keeping only the place id, so names and addresses are fetched each time they are shown (cost per view). Alternatives: Foursquare or Overture open data (can be stored), or the kids'-activity places already collected for KidSpark. Default: Google Places (New), place id only, details through the API with a short cache.
- [x] **Q8 Are the time slots right?** **Answered (owner, 2026-11-16): the default, as built.** (doc) Morning 9–12, Afternoon 1–4, Evening 4–7; 12–1 is not covered. Default: as designed; the slot times are one setting in `src/lib/rules/config.ts`, so changing them later is a one-line change.

## Needed before the beta (Phase 3)
- [x] **Q1 Cancelling** **Answered (owner, 2026-11-16): the default, as built.** (doc). Should cancelling ask to confirm and tell everyone (in the app and by text)? Today the prototype just removes the playdate. Default: yes (KD-15): a confirmation, invites show "Cancelled", Kindred users get a push if they have it, text friends get a short text through a Text button.
- [ ] **Q11 Notifications for parents who use Kindred.** The doc says app users get in-app updates. A web app can push only when added to the Home Screen (iPhone: iOS 16.4+). Default: Web Push for a new invite, confirmation, update and cancellation (never for other parents' answers) when the parent has turned it on; for a Kindred friend without push, the organizer gets a Text button for them too, so nobody misses an invite.
- [ ] **Q13 Privacy text and children's data.** Kindred stores children's first names and ages. Default: a plain privacy page and a consent line at Setup before the beta, reviewed against PIPEDA (Canada). Who reviews it?

## Feedback round 1 (2026-11-15, from the first tester)
- [x] **Q24 Home as one list.** **Answered (owner, 2026-11-15): yes, as the default; built in T29.** The tester found Needs you, Upcoming and Waiting for answers too many separate boxes. Default: one list, soonest first, with one status line per card (coral when it needs you); this replaces KD-13's sections (T29).
- [x] **Q25 Which tabs.** **Answered (owner, 2026-11-15): yes, as the default; built in T32.** The tester wants Friends in the tab bar, with groups made there. Default: Home · Friends · Places; groups move inside Friends, and Ask and Explore become one Places tab (answers Q7) (T32).
- [x] **Q26 Not storing friends' phone numbers.** **Answered (owner, 2026-11-16): yes, as the default (T33, T34).** The tester doesn't want Kindred to keep phone numbers, and asks how to add friends from the phone's contacts. iPhone browsers can't open the contacts list (Q15), and today every text needs the stored number (Q12). Default if approved: share each invite through the phone's share sheet, where the parent picks the person from their own contacts; Kindred keeps only the keyed hash for "has Kindred" and drops the number; plus an Invite to Kindred link that makes two parents friends without a number (T33, T34). Cost: one more tap per friend, and Kindred can't show a friend's number on another phone.
- [x] **Q27 Check-ins during a playdate.** **Answered (owner, 2026-11-16): yes, as the default (T35).** The tester wants parents to tell the others how it's going, with taps. Default: parents who are coming (organizer included) can post a few fixed check-ins plus an optional note of up to 80 characters, from 30 minutes before the start to 1 hour after the end; no photos of children; shown on the playdate page and the invite pages; never sent by the server (T35).
- [ ] **Q28 Links for friends away from the home Wi-Fi.** Today links only work on the laptop's Wi-Fi. Default: finish staging (T04), which Add to Home Screen and push (T20) need anyway; a temporary tunnel only if staging has to wait (T28).

## Mock-up round 2 (2026-11-18, the tester's second mock-up)
- [ ] **Q29 Chips instead of status lines.** The mock-up shows "✓ Confirmed" / "Pending" tags and one small chip per family (✓ Dev, ✕ Maya); DESIGN.md asks for status lines, not badges. Default: take the mock-up's look and rewrite DESIGN.md "Visual design" to match (T37, T36); every chip also carries its words for screen readers.
- [ ] **Q30 More than one child.** Q4 said not in v1; the mock-up asks "Who's this playdate for?" and marks which of your kids each friend knows. Default: yes, as in the mock-up (T41, T42); a friend with nothing marked counts as your first child's friend.
- [ ] **Q31 "Free to play" status.** The mock-up lets a parent mark a child "Free this afternoon" for friends to see; nothing is sent. Who sees it? Default: only parents on Kindred who are friends both ways (each has added the other), at most 2 days, never on invite links (T45).
- [ ] **Q32 Chat.** The mock-up has one-to-one messages, group chats in place of groups, and a chat on each playdate. That means storing what parents write and deciding how long to keep it, and it works against the doc's "without the group-chat back and forth". Default: not now, and groups stay; if wanted later, start with a chat on each playdate only, kept until the 30-day clean-up (T46).
- [ ] **Q33 Weather on Home.** The mock-up shows "8° Partly cloudy · Dry until 4 PM, a good afternoon for the park". It needs a weather service and the parent's rough location. Default: not now (T47).
- [ ] **Q34 A map in Places.** The mock-up names Apple Maps (MapKit JS needs an Apple Developer membership); it goes with the places provider (Q6). Default: decide together with Q6; until then Places stays a list (T48).
- [ ] **Q35 "Text me when it's confirmed" for friends without the app.** The mock-up offers it on the link page, but Kindred never sends texts itself and keeps no friend's number (Q26). Default: no; the organizer shares the update, and the link page always shows the latest state.
- [ ] **Q36 Confirming with no yes.** The mock-up allows "Confirm anyway? No one has said yes yet." KD-09 needs at least one yes. Default: keep KD-09.
- [ ] **Q37 What families who said no see once it's confirmed.** In the mock-up the playdate disappears for them; today they still see it, confirmed, and can change their answer (KD-07m). Default: keep today's behaviour.
- [ ] **Q38 "See who's on Kindred" from the whole address book.** The mock-up asks to allow contacts; the privacy rule is that only contacts a parent picks are checked, and iPhone browsers can't read the address book anyway. Default: no; the Invite to Kindred link (T34) and adding a friend cover it.
